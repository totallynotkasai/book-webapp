# P1-QA-01: performance pass (13 October 2026)

DESIGN.md §12.3's budgets, measured on this build before the PoC review. **Every budget is met**, at 4× and at 6× CPU slowdown, and in the Android app on the emulator. Nothing needed an issue filed. One change came out of it: the cold open measured 2.6 s at 4× CPU over 4G, over budget. The reader now downloads its engine, the reading fonts and the import worker at the same time instead of one after another, and the test server now compresses files as real hosts do; together they bring it to 1.4–1.5 s.

## How it was measured

| Where | What | How to repeat |
|---|---|---|
| Desktop Chromium, slowed down | All seven budgets | `npm run build`, then `npm run test:perf -w @book/web` (`PERF_CPU=6` for 6×). `apps/web/e2e/phone.perf.ts` |
| The Android app on the emulator | Cold open, cached Chapter, page turns, re-layout | `npm run apk:tester -w @book/web`, install, then `node apps/web/scripts/perf-android.mjs --fresh [--cpu 4]` |
| CI, on every PR | The reader route's JavaScript; the import pipeline | `npm run budget -w @book/web` after a build; `packages/text-pipeline/src/ingest.budget.test.ts` in `npm test` |

- **Reference device and slowdown.** The owner's phone is busy with another project (D-028), so the "phone" here is a desktop Chromium slowed down with DevTools CPU throttling, 4× (the usual stand-in for a 2023–24 mid-range phone such as the Galaxy A15) and 6× (a harsher check). The window is a 412 × 915 phone at 2.625× pixel density with touch.
- **Network.** The cold open runs over a 4G link as Lighthouse and WebPageTest model it: 9 Mbit/s down, 1.5 Mbit/s up, 170 ms round trip. The test server gzips text files, as GitHub Pages does.
- **Web Workers aren't slowed by DevTools throttling.** Opening a seeded Book for the first time, and importing, process the EPUB in a worker. The spec times the worker's jobs (`pipeline:ingest`) and adds them again (slowdown − 1) times, so the figures below include a worker as slow as the page. The pass/fail check uses that figure.
- **Timings come from the page itself** (`performance.now()`, Event Timing, MutationObserver on the reader's reported range), not from the test runner's polling.
- **The emulator** runs at the PC's speed, so its 1× figures show a real Android WebView (133, below 140: the padded-WebView case, ADR-004) rather than a slow phone. Its 4× runs slow the WebView's main thread only, like desktop.

The narration lag uses silent audio of each Chapter's real length with the real Sync Maps (as the narration E2E spec does); on Android the native player's clock is extrapolated in the WebView (P1-LAY-04 measured that path).

## What changed

- **Parallel loading on open** (`Reader.svelte`): the reader engine's code (`createEngine`) and the reading fonts start downloading as soon as the reader opens, and the simulated backend warms its import worker (`Pipeline.warm`) while the EPUB downloads. Before, over 4G at 4× and without compression: route code → EPUB → import worker (283 KB uncompressed) → fonts → engine, 2.6 s in all. After both changes: 1.4 s.
- **The test server gzips** HTML, JavaScript, CSS, JSON and SVG (`scripts/serve.mjs`), as static hosts do, so downloads are measured at their real size.
- **Worker jobs are timed** with `performance.measure('pipeline:<op>')`, visible in the browser's performance tools too.

## Headroom and watch points

- **Reader route JavaScript** has 34 KB of headroom. Zod (about 32 KB gzipped) is on the route because `@book/core`'s schemas validate what the reader reads; a slimmer validator for the reader's few schemas is the obvious saving if the budget gets tight.
- **The cold open includes the simulated backend's work**: processing the EPUB in the browser (0.15 s on the emulator, about 0.6 s with the worker slowed 4×). With the real backend (Phase 2) the processed Revision is downloaded instead, so this part goes away.
- **On the owner's phone** (when it's free, D-028): run `node apps/web/scripts/perf-android.mjs --fresh` with the tester app installed. `--fresh` deletes the app's data on that phone, so leave it out to measure a warm open. The device checklist lists it.
